# 调用示例

以下都是假设场景，不是任何项目的实际需求、模型能力或执行记录。路径按目标项目真实约定调整。

## 1. 自研 Harness，从零设计

> 使用 $agent-backend-workflow，为聊天机器人后端设计自研 Harness。团队使用 Python，先接入一家第三方模型，需要流式聊天和多轮会话。本轮只设计，不写业务代码。

走 scaffold，读取现有工程/约束，给出 API、会话、Harness、provider 和存储边界及一个完整切片。明确断线策略与是否需要跨进程续跑，不因用户说“会话”就承诺持久化执行。未指定模型则提出基于必需能力的推荐/待定项，不能编造 endpoint。设计写入项目架构文档后结束，不创建服务代码。

若用户改为“搭建并跑通切片”，则在授权范围内继续工程、合同测试与真实冒烟；没有凭据可先验证 Fake，但交付必须注明真实接入待验证。

## 2. 需求与实现一次完成

> 使用 $agent-backend-workflow，增加查询订单物流功能：用户必须登录，只能查自己的订单；用现有只读物流接口，允许多轮补充订单号。更新 PRD 并实现。

走 prd → build。先查已有订单归属和工具能力，写一份轻量 change 并同步主题 PRD，不重复索要开工确认。可观察验收包括：

- AC1：已登录且订单属于本人 → 提供订单号 → 返回与物流接口一致的事实；缺少物流信息时明确说明未知。
- AC2：订单属于其他用户 → 请求查询 → 服务端拒绝访问，不返回他人物流内容。
- AC3：信息不足 → 继续对话补充订单号 → 在同会话完成查询，不误用其他会话的信息。
- AC4：物流接口失败 → 请求结束 → 提供可理解的失败，不虚构节点、不宣称查询成功。

工具执行前用真实身份校验订单归属，不信任模型传入 user ID。确定性测试验证越权与失败，代表性多轮评测验证工具选择和回答忠实性。样本数与效果门槛根据已有约定；没有门槛不自行写“准确率 99%”。

## 3. 增加第二家模型，不重写 Harness

> 使用 $agent-backend-workflow，保留现有模型 A，新增模型 B 的 adapter，支持现有流式和工具查询。这次不做自动故障切换。

走 build + providers，核对 B 的具体 API/型号和现有工具消息映射，接通装配路径，做碎片流、工具参数、结束原因及真实冒烟。复用同一任务集比较 A/B 的结果与成本。B 缺少必需能力时显式报告，不静默退化成文本工具。自动切换不在本轮范围，不能顺手实现路由平台。

## 4. 超时导致写工具重复执行

> 使用 $agent-backend-workflow，机器人创建工单时工具超时，重试后产生两张工单，修复它。

走 fix，不创建产品变更。用测试替身复现“下游已写入，客户端未收到响应”的窗口，查下游业务幂等键与结果查询。修复使同一操作复用稳定幂等身份；无下游支持且结果未知时阻止自动重试，按既有异常处理核实。验证工单真实数量/工具调用结果，不能只让模型回答“只创建一次”。不声称本地事务实现了跨系统 exactly-once。

## 5. 只刷新预算规则

> 使用 $agent-backend-workflow，把单次运行最多 4 次模型调用改成 6 次，其他条件不变。仅更新当前 PRD。

走 refresh，一份 change 写完整新规则，并保留原有截止时间、重试计数口径、工具权限和耗尽后的行为。若既有文档没定义调用次数是否含重试，标明该歧义并核对现有事实。只更新受影响验收和实现缺口，不改 prompt、配置或代码。同步后可归档；文档目标改成 6 次不等于后端已放宽限制。

## 6. 长上下文效果退化

> 使用 $agent-backend-workflow，修复多轮聊天压缩后忘记用户约束的问题，保留现有模型与架构。

走 fix + harness + evaluation，固定脱敏对话和工具数据，比较压缩前后上下文，区分摘要漏事实、截断工具对和会话串扰。若既有正确行为是保留明确限制，这是恢复行为，不强制新 PRD。补最小长对话用例，既检查必须保留的约束，也比较真实模型结果；不自动引入向量库或长期记忆。

## 7. 旧变更与新目标冲突

假设历史 change 曾把模型调用上限从 4 改成 6，现行 PRD 已接受 8；另一个模块仍停留在 4。用户要求补齐该模块时直接实现当前 8，不能重放旧 change 把规则改回 6。同步前若发现独立编辑补充了超时提示，保留该修改；只有同一规则的实质冲突才需要决策。

## 8. 接入资料或凭据缺失

> 使用 $agent-backend-workflow，按官方文档接入模型 B，但目前没有测试 Key。

完成能独立执行的 adapter、fixture 合同测试与配置说明；测试密钥用项目环境变量，不写入技能或仓库。明确“本地合同测试通过；真实厂商调用和效果评测未运行”，列出最小补验方式，不虚构 token、账单或成功回答。已有授权不需要因缺 Key 再问是否可以先写代码。
