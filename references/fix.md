# 故障定位与修复

用于恢复已接受行为。默认不新建 PRD/change，不全仓审计或顺便更换模型/依赖。

1. 从请求示例、失败测试或脱敏 run/trace 确认症状、预期和范围。查相关代码与已接受规则；信息能从项目找到就不问用户。
2. 沿真实调用链定位：API/鉴权 → 会话/运行状态 → 上下文 → provider 流 → 工具与副作用 → 输出/存储。区分 Harness 缺陷、厂商故障、工具失败、数据问题和模型效果退化，不把所有失败归为“模型不稳定”。
3. 建最小复现。确定性故障用固定响应、碎片事件、故障注入或存储状态；模型问题固定用例、prompt、模型及工具环境，保留重复试验的差异。安全回放用工具替身，不重放真实写副作用。
4. 做有证据的最小修复。循环失控先查停止条件，重复写查幂等与恢复边界，混合流查 attempt/事件归属，越权查服务端资源权限；不能只改系统提示词掩盖这些问题。
5. 验证原症状已消失。回归测试应能在旧逻辑失败、修复后通过；模型效果问题加入代表性评测并查相邻能力退化。按实际共享调用者扩大验证，不默认全厂商全场景重跑。

无法复现但代码能证明缺陷，可有依据地修复并说明限制。厂商临时故障不能凭一次成功重试判定根因已修复；没有凭据时不宣称线上恢复。日志与回放不得携带密钥或未经允许的用户正文。

若发现预期本身要改变，转 [refresh](refresh.md) 记录语义差量；内部 bug 恢复继续本流程。跨会话交接需要时在已有 issue/持续文档记录根因与下一步，不强制新建故障知识库。

交付说明根因或仍存疑点、修复位置、实际验证和剩余影响。只有本次确实改动产品目标，才更新相关需求规则。
