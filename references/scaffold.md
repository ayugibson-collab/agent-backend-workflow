# 工程与 Harness 设计 / 搭建

适用：新后端、新 Harness 或明确要求的模块边界调整。先读真实工程和 [架构原则](architecture-principles.md)，涉及运行循环时读 [Harness](harness.md)。

## 执行

1. 区分“设计”与“搭建”，选一个代表性切片，例如带会话的流式聊天，或一次只读工具查询。只设计就交付方案，不生成业务工程。
2. 调查已有请求入口、身份、存储、模型客户端、工具与测试，说明哪些可复用以及实际缺口。沿用已有栈；空工程根据团队语言、部署约束、流式/并发需求给出一个推荐，关键选择未知才澄清。
3. 明确 API、会话/运行、Harness、provider adapter、工具执行、持久化和追踪的职责。它们是逻辑边界，默认可在一个服务内实现；不为画图拆微服务或为每个类建接口。
4. 用 [SCAFFOLD 模板](../assets/templates/SCAFFOLD.md) 按需保留设计，写清运行状态所有权、I/O 边界、流式事件、失败语义、重试归属和最小验证方式。需要恢复才设计检查点，需要后台任务才引入队列/worker。
5. 已授权搭建时接通真实切片：入口 → 身份/会话 → 上下文 → 一家实际需要的模型 → 输出/落库；工具属于切片时再接入。生产所需 I/O 不用未标注的内存或 Fake 替代。
6. 记录并执行真实启动、静态检查和相关测试；从入口验证切片和相关失败路径。开发用 Fake 能验证控制流，真实模型可用性要另行验证；缺少凭据时准确标明限制。

## 设计完成的依据

- 一个用户动作能穿过完整调用链，关键入口和状态归属明确。
- 必需厂商能力已核对，未核实项不当作可用；模型接入参考 [providers](providers.md)。
- 可观察结果不依赖阅读全部日志：至少能关联请求、run、模型和工具执行及结束原因。
- 项目已接受的预算、鉴权、取消和失败要求有明确执行位置。
- 有必要的合同测试/集成验证方式；模型行为验收按 [evaluation](evaluation.md) 定义。

只在确有取舍时记录扩展触发条件，例如后台长任务需求出现后才引入持久化调度。现有架构内为完成需求所需的局部调整属于正常开发；更换栈、迁移服务或扩大系统边界须以本次授权为依据，不因发现缺口自动执行。
