# 工程测试与 Agent 评测

目标是验证“后端控制正确”和“模型与 Harness 合起来完成任务”。复用项目已有测试/评测工具，不默认引入平台或要求固定数量用例。

## 按变化选择验证

- **确定性逻辑**：鉴权/归属、状态迁移、预算、请求/业务幂等、取消、参数校验；普通测试断言精确结果。
- **协议合同**：厂商请求/流事件、工具配对、拒绝/截断/错误；用固定 fixtures 或脱敏录制回放。
- **服务集成**：从 API 到存储、Harness、模型/工具替身再到输出，覆盖本次实际调用链。持久化保证用真实测试数据库/等价环境验证，内存 Mock 不足以证明事务与多副本并发。
- **Agent 效果**：模型、prompt、工具定义/选择、上下文或路由变化时，固定任务集比较真实模型下的业务成功与约束满足。
- **容量和恢复**：只在改动影响并发、慢客户端、超时或后台恢复时补相应验证；不为小改动自动压测全系统。

Mock 不验证模型效果，真实模型调用也不能替代确定性状态机测试。评测基础设施失败、厂商不可达与 Agent 未完成任务分别归因，同时报告用户视角的总体失败，不能从分母里静默剔除。

## 从 PRD 建立最小有效评测集

先复用已有验收、人工检查及脱敏真实失败，选典型成功、边界和失败任务。相关时加入多轮澄清、缺少事实不编造、工具不可用、恶意外部指令、权限拒绝、长上下文、取消/预算及降级。没有检索能力就不造 RAG 评测，有写工具才测其副作用。

单个用例可包含：

```text
id / 关联验收
用户输入或多轮任务 + 初始会话/业务状态
可用工具、固定外部数据/模拟环境、授权主体
预期最终结果与允许行为 + 禁止行为
确定性断言 / 效果评分规则 / 必要的预算约束
```

最终状态优先于模型说辞：订单真实状态、写操作次数、引用来源、工具输出与回答的一致性。只有协议、权限或业务流程确实要求时才断言唯一工具轨迹；合理的不同工具路径不能一概判错。用例和答案/评分信息分离，运行时不把标准答案泄露给被测 Agent。

## 评分与比较

能用代码判断的条件用代码，例如是否越权、是否写了两次、结果是否符合 schema。开放式答案采用明确 rubric，可用模型评分或人工抽查；LLM judge 固定版本与评分提示，隐藏候选版本身份并校准人工样本，关注位置偏差和不一致。不要仅让被测模型宣称自己成功。

更换模型、prompt、工具 schema 或上下文策略时：

1. 固定任务数据、工具环境与评分版本，记录基线和候选的代码/配置、模型及运行日期。
2. 根据波动和风险选择重复次数，记录每次 trial；temperature=0 或 seed 不构成完全确定性保证。
3. 报告样本数、重复次数、业务成功率、相关切片失败及关键禁止行为；避免总平均掩盖某厂商或关键流程退化。
4. 按任务比较首 token/总时延、调用/工具次数、token usage 和成本。估算与实际分开，缺失 usage 标未知，不能按 0 成本。样本太少时不制造可靠 p95 或普遍成功率结论。
5. 对照已有门槛/允许退化判断；没有门槛时输出观测和建议，不能事后为“通过”降低标准。训练/调优样例与保留回归集分开，避免仅针对固定题目优化。

默认关注单次成功率和重复试验稳定性。任务允许多次尝试时才使用 pass@k，并给出尝试次数和代价；“试多次至少成功一次”不能冒充单次成功率。

关键权限/副作用约束可作为硬失败项，但只以已接受要求为依据。一次真实请求成功不是效果验收；评测通过也只覆盖当前任务集与环境，不是生产保证。

## 证据与闭环

必要时使用 [EVAL 模板](../assets/templates/EVAL.md)，或沿用项目已有报告格式；不要求每个 Bug 生成评测报告。保留版本、命令、样本与 trials、结果、代表性失败 trace 和未验证项，记录数据来源和脱敏方式，不把用户秘密提交到仓库。

在线观测用于发现真实分布问题，离线回归用于可控比较。代表性线上失败经允许和脱敏后加入评测，修复后用同一用例验证；不要自动收集全部用户对话。发布时沿用已有的灰度、回滚和告警机制，prompt/model/config 一并可追溯，避免只回滚代码却保留有问题的配置。

环境缺失时给出可执行的最小补验命令/前提，标记实际未运行；不以生成了一份用例文件冒充已经完成评测。
