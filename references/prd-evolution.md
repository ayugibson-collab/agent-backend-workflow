# PRD 的轻量演进

沿用 app-workflow 的当前规范、增量变更、同步与归档思路，不依赖 OpenSpec CLI 或固定审批链。

## 三类记录

- `docs/prd/<topic>.md`：当前已接受目标、验收、按能力/厂商/环境的真实交付缺口；不代表全部实现或上线。
- `docs/changes/<date-topic>/change.md`：一次语义变化及必要结果。普通变更只需这一份文件。
- `docs/changes/archive/<date-topic>/change.md`：结束任务的历史，不再作为活跃待办。后续任务读最新 PRD。

代码、prompt、模型参数或上下文策略变化不必全部变为产品 change：仅调整内部实现以达到既有目标，记录代码与验证即可；改变用户可见行为、权限、数据用途、成本承诺或支持范围，才更新相关产品规则。恢复既定行为、错字和纯结构整理不强制建 change。

## 差量与同步

使用 [CHANGE 模板](../assets/templates/CHANGE.md)，只保留使用的类别：

- ADDED：完整新增规则、适用条件和验收。
- MODIFIED：必要旧规则及修改后完整规则，保留未改变的条件、限制和例外；不能只有“3 次改为 5 次”。
- REMOVED：被移除规则、原因、验收替代及必要的数据/兼容处理。

规则适用范围与本轮实施范围分开。例如共同规则涵盖厂商 A/B，本轮只实现 A，B 的缺口持续记录；不能自动宣称 B 已完成。

build / sync 前重读最新 PRD，对比旧含义、本次目标和最新正文，按语义合并受影响段落。保留独立编辑；未提及不等于删除。目标已在正文则不重复套用；被后续已接受规则取代的旧 change 不得重放。不能仅按文件时间判定哪个方案获接受。

用户明确要求更新 PRD 或实施新规则即已有相应授权；候选草案不能覆盖基线。同一规则存在实质冲突且用户未作选择时，仅暂停依赖该决定的部分。更新正文与关联验收，避免把新规则追加到旧矛盾规则之后。

只有受影响场景的旧验证结论失效，无关证据保留。更新当前 PRD 的待实现/待验证范围；厂商协议差异与尚未实现分别表述。落后的实现直接追最新目标，不依次实现过时中间版本。

## 归档与结构调整

本次授权工作结束，已接受规则与余留工作已进入持续文档后可归档；仅文档任务也可以结束。候选方案未接受时注明未同步，必要的后续决策留在已有持续文档的待定部分。同步冲突未解决不能声称同步完成。

移动 change 时修正相对链接和指向它的引用；之后不继续维护历史待办。归档不证明工程测试、模型评测或上线完成。

拆分、合并、重命名时保持规则唯一归属，更新引用与在途变更，保留验收含义和交付缺口。确有多主题共享才提取共享 PRD。历史归档不随当前结构改写，可在当前文档说明旧路径去向。模板不能自动保证正确合并，历史依靠真实版本控制。
