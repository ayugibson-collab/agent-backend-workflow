# 按需求开发

输入可以是现行 PRD、已接受变更，或足够明确的简短需求。完成授权范围内的代码与验证，不在文档完成后要求再次开工。

## 1. 核对目标和真实路径

重读最新 PRD、仍适用的本次 change、项目约束和真实入口。目标已同步就直接使用；旧差量不得覆盖新规则。无 PRD 的新语义需求先写最小规则和验收并按授权同步，见 [prd](prd.md)；实现既有目标不重复建 change。

局部查找可复用的 API、会话、模型、工具和测试能力，沿入口追到实际调用。检查现有边界是否能承接本次状态、并发和失败语义，用几句话说明依据。正常局部实现自主推进；需要更换框架、迁移现有数据或扩大服务范围时说明具体影响，已有授权则执行。

## 2. 把验收映射到实现

对受影响验收确定修改位置和验证方式，不另建强制任务台账。优先做垂直切片，避免先堆全部接口和空实现。

- 请求/API 变化：输入校验、调用方兼容、身份/会话归属、响应与错误语义。
- Harness 变化：读 [harness](harness.md)，落实涉及的状态、终止条件、预算、取消和工具调用。
- 模型接入变化：读 [providers](providers.md)，核对能力，接通真实 adapter，明确失败与降级。
- 工具变化：服务端 schema/权限校验、业务执行结果、适用的幂等与超时；外部工具返回不授予新权限。
- 数据变化：复用迁移机制，明确新旧服务/已有会话的兼容性；生成和验证迁移不等于运行生产迁移。
- prompt、工具定义、上下文或模型路由变化：版本化相关产物，并按 [evaluation](evaluation.md) 检查效果退化。

只实施本次需要的规则。已有代码、schema、prompt 或 SDK 类型能作为契约时复用，避免再维护平行规范。

## 3. 验证真实行为

先跑受影响的确定性测试和项目要求的构建/静态检查，再按变化运行 adapter 合同测试、服务集成和相关模型评测。使用可控制的时钟、工具替身和流事件复现超时/取消等边界，不靠真实模型随机触发。

验证范围依风险扩展：普通文字修正无需模型评测；provider 解析修改覆盖相关事件和真实厂商冒烟；工具写操作覆盖重试/恢复下的副作用；上下文压缩覆盖多轮信息保留。已有必需 CI 继续执行。

Mock、脱敏回放只证明本地逻辑；真实厂商冒烟证明当时该模型/API 可接入；评测集通过只证明该测试分布下的结果。缺少凭据、网络或数据时完成独立部分并标记待验证，不能造“通过”记录。

## 4. 收尾与交付

检查本次差异，清除临时调试、硬编码密钥和未接入的占位实现。按改动更新项目接口、架构、运行说明与当前 PRD 的证据和缺口。普通任务不生成独立报告包。

记录实际命令、环境、代码/配置/评测版本及结果；重要模型行为变化用基线对比，不能只报告新版本分数。当前规则和余留工作已持续记录后可归档 change。

部署在本次授权范围时，复用项目发布流程，先核对环境、配置/迁移兼容与回滚目标，再实施并检查关键错误、时延、成本和效果指标；可按项目条件灰度。异步运行升级还需考虑在途 run 与旧检查点。未授权部署时交付可审阅代码和验证即可。

最终说明：做了什么、证据是什么、尚缺哪项真实验证；功能、模型质量和部署状态分别表述。
